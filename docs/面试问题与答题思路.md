# 项目相关面试问题与答题思路

> 这份清单覆盖“介绍项目”“架构设计”“LLM 工程”“可观测”“评估体系”“后端细节”“开放性追问”七类。
> 每题都给了**答题思路**（不是标准答案），核心是让你能讲清楚“为什么这么设计”。

---

## 1. 项目介绍类

**Q1：请用 30 秒介绍这个项目。**
- 一句话：一个解决“不知道吃什么”的多 Agent 对话式饮食推荐系统。
- 三个要点：多 Agent 编排（意图→澄清→检索重排→LLM 生成理由）、全链路 Trace 可观测、离线批量评估闭环。
- 一句话价值：把 LLM 从“不可控的黑盒”变成“可回放、可评估、可兜底”的推荐引擎。

**Q2：请详细讲讲整个对话链路。**
- 用户消息进入 `/chat` → Orchestrator 加载会话状态、开启 Trace → IntentAgent 识别意图+槽位 → IntentRevise 规则矫正 → 槽位合并 → 路由分发：
  - 信息不足 → ClarifyAgent 追问；
  - 推荐/调整 → 检索（JSON_OVERLAPS）→ 重排（7 维打分）→ RecommendResponseAgent 生成理由 → RiskGuard 合规检查；
  - 多餐 → MealPlanService 逐餐检索 → PlanResponseAgent 生成方案；
  - 健康风险/闲聊 → 固定文案。
- 全程每步埋 Trace 事件，结束时落库。

**Q3：这个项目和你之前做的纯 Java 后端项目有什么区别？**
- 相同点：分层（Controller/Service/Mapper）、数据库、事务、异常处理、状态机思维都在。
- 不同点：多了“LLM 这个不确定依赖”，所以要多做三件事——结构化输出约束（JSON+词典）、确定性兜底（规则降级）、可观测（Trace）+可评估（离线评估）。
- 一句话：Agent 工程 = 后端工程 + 对不确定性的工程化治理。

## 2. 架构设计类

**Q4：为什么要拆成多个 Agent，而不是一个 Agent 干完所有事？**
- 单一职责：意图识别、澄清、推荐生成各自独立，输出互不干扰；
- 可独立优化/独立评估：意图准确率可以单独测；
- 可独立降级：某个 Agent 挂了只降级它自己。
- 代价：调用次数变多、链路变长，所以用轻量模型（qwen-turbo）承担简单任务控制成本。

**Q5：为什么需要编排层（Orchestrator）？Agent 不能自己决定下一步吗？**
- 类比后端：Controller 不会让每个 Service 自己决定返回什么，状态机必须收敛。
- 如果让 Agent 自己路由，同一句话可能这次走 A 分支下次走 B 分支，不可测试、不可回放。
- 编排层的职责：会话状态读写、路由、调用顺序、落库、兜底。Agent 是无状态“函数”。

**Q6：会话状态为什么设计成“编排层唯一写”？**
- 保证状态一致性：多人改会乱；
- 可回放：给定相同状态必然走相同分支；
- 职责清晰：`SessionStateService` 只管持久化，`Orchestrator` 只管状态流转。

**Q7：为什么“选菜”用规则检索重排，而不是直接让 LLM 选？**
- 防幻觉：LLM 会选库里没有的菜；规则检索保证结果一定来自数据源；
- 省成本：不用把整个餐食库塞进 prompt；
- 可解释：`matchScore` 是确定性的，方便 Trace 和评估。
- 核心观点：**LLM 擅长表达，不擅长精确检索**。

**Q8：检索用 JSON_OVERLAPS 的召回 + 规则打分重排，为什么不直接写复杂 SQL？**
- JSON_OVERLAPS 是“宽召回”：任一维度命中就进候选，保证不遗漏；
- 精排放 Java：打分逻辑（重叠率、排除已推荐）可复用、可单测，也方便以后换算法（向量召回等）而不动 SQL。

**Q9：多轮对话的上下文是怎么管理的？为什么不用 Agent 自带 memory？**
- 不用 memory：不可控、会膨胀、跨轮污染。
- 做法：每轮从 `diet_messages` 取最近 3 轮，摘要压缩（120 字）后显式拼进 prompt。
- 优点：上下文受控、可审计、token 可控。

## 3. LLM 工程类

**Q10：怎么防止 LLM 输出幻觉？项目里用了哪些手段？**
- 四层：
  1. 槽位幻觉 → 词典约束（prompt 写明只能用 slotOptions 的候选）+ `SlotJsonPicker` 代码二次过滤；
  2. 餐食幻觉 → 检索层定死候选，prompt 强制 `mealId` 必须来自候选；
  3. 内容幻觉 → `recommend-response.txt` 禁止编造餐食特征、禁止绝对化用语；
  4. 输出幻觉 → 安全守卫 `RiskGuardService` 兜底。
- 一句话：**prompt 约束是“软约束”，代码校验和规则兜底是“硬约束”**。

**Q11：LLM 输出不是合法 JSON 怎么办？**
- `LlmJsonService` 先兼容 ```json 围栏、按首尾花括号截取；
- 解析失败不抛给用户：IntentAgent/ClarifyAgent 等捕获后走关键词/模板兜底；
- 评估时 Judge 失败返回 null，不阻断。
- 关键原则：**LLM 的失败是常态，必须有降级路径**。

**Q12：为什么意图识别用 qwen-turbo，推荐生成用 qwen-max？**
- 意图识别是高频、简单任务：要快、要便宜 → 轻量模型；
- 推荐理由是低频、质量敏感任务：要表达好 → 主模型；
- 这是 Agent 工程常见的“模型分级”策略。

**Q13：如果 LLM 超时或挂掉，系统会怎样？**
- 不会中断：意图走关键词 Fallback，澄清走模板，推荐走模板理由+模板话术；
- 兜底会被 Trace 记录（事件类型可区分），线上可看出哪些请求降级了；
- 用户最差得到模板化回复，而不是报错。

**Q14：多 Agent 之间怎么传数据？都是 JSON 吗？**
- 是。每个 Agent 的输入输出都是结构化对象（IntentResult/ClarifyResult/RecommendResult）。
- 好处：Agent 间解耦、可单测、可 Trace（payload 直接序列化进 trace_json）。

## 4. 可观测类（Trace）

**Q15：为什么 LLM 应用需要 Trace？和普通日志有什么区别？**
- 普通日志是“发生了什么”，Trace 是“每一轮请求在每个节点的输入/输出/耗时/Token”。
- LLM 黑盒 + 多 Agent 链路：没有输入输出快照，线上问题无法复现，因为 LLM 输出不可重放。
- 本项目 Trace 的价值：逐步回放、定位是哪一环退化、为离线评估提供原始数据。

**Q16：Trace 是怎么实现的？讲讲 ThreadLocal 的作用。**
- `AgentTraceService.openTrace()` 创建 `TraceScope`（AutoCloseable）放入 ThreadLocal；
- 同一请求线程内 `recordEvent/callAgent` 都往当前 scope 里追加事件；
- 请求结束 `try-with-resources` 触发 `close()` → 序列化写库 → 清理 ThreadLocal（防止线程池复用污染）。
- ThreadLocal 的坑：必须 finally 清理；异步线程不共享（本项目同步处理所以可用）。

**Q17：为什么 Agent 调用要统一走 `callAgent()` 而不是各调各的？**
- 一次埋点全链路复用：模型名、耗时、Token 自动记录；
- 保证格式统一：所有 `AGENT_CALL` 事件结构一致，评估时按 `totalTokens` 汇总 Token 成本才有意义。

**Q18：Trace 落库失败会怎样？为什么这样设计？**
- 只打 warn 不抛异常，业务照常返回。
- 原则：**可观测是增强，不能成为可用性的反向依赖**。

## 5. 评估体系类

**Q19：为什么需要离线评估？在线看不就行了吗？**
- 人工看不完所有对话，且没有量化标准；
- 改 prompt/规则后效果是变好还是变差，需要可复现的批量度量；
- 离线评估 = LLM 应用的“回归测试 + 监控大盘”。

**Q20：讲讲三源加权（60/10/30）的设计。**
- 规则分 60%：意图/槽位/澄清准确率、Token、延迟、fallback、安全、幻觉——客观可复现，是主干；
- LLM Judge 10%：回复解释质量和自然度——主观体验，LLM 打分本身不可靠，所以低权重；
- 用户反馈 30%：真实用户信号——稀疏但有价值。
- 缺失归一化：没标注的指标按 null 跳过，不当作 0 分误伤。

**Q21：人工标注（gold label）在评估里起什么作用？**
- 提供“标准答案”：`expected_intent / expected_slots / expected_clarify_action`；
- 驱动准确率类指标（intentAccuracy/slotAccuracy/clarifyNecessityAccuracy）；
- 低分样本 → 标注 → 迭代 → 再评估，形成“Trace 标注—批量评估—指标驱动迭代”闭环。

**Q22：LLM Judge 有哪些局限？怎么缓解？**
- 局限：Judge 本身可能误判、有偏好、不稳定；
- 缓解：只让它打“主观表达”两维（解释质量/自然度），准确率类交给规则；权重只给 10%；失败返回 null 不参与。

**Q23：幻觉控制指标（hallucinationControl）是怎么算的？**
- 从 Trace 里收集两件事：重排候选的 mealId 集合（`MEAL_RANKED`）和最终响应卡片的 mealId 集合（`RESPONSE_READY`）；
- 若最终卡片集合是候选集合的子集 → 无幻觉；否则视为幻觉。
- 这就是“把 Trace 当测试集”的典型例子。

## 6. 数据库 / 后端细节类

**Q24：7 维槽位为什么用 JSON 数组存？怎么查询？**
- 每道菜可以打多个标签（如早/午/晚都能吃），用 JSON 数组自然；
- 查询用 MySQL 8 的 `JSON_OVERLAPS(column, ?)`：两数组有交集即命中；
- 索引局限：JSON 函数不走普通 B+ 树索引（可加生成列+函数索引），数据量大了要考虑。

**Q25：为什么个人餐食和公共餐食放同一张表？**
- 结构完全一致，用 `source_type` 区分（PUBLIC/PERSONAL）+ `owner_user_id` 归属；
- 检索 SQL 用 `choose` 按 sourceMode 过滤，避免混查；
- 好处：一套 CRUD 代码管两种数据源。

**Q26：并发下同一会话的多次请求怎么保证状态一致？**
- `ConcurrentHashMap<String, Object>` 按 sessionId 拿锁对象，`synchronized(lock)` 串行处理同一会话。
- 局限：单机内存锁，多实例部署需要换分布式锁（Redis）。
- 面试加分：能主动说出单机锁的边界。

**Q27：为什么推荐要用 lastRecommendations 排除已推荐？**
- “换一批”场景需要不重复；如果每次都推荐同一批，体验差。
- 实现：SessionState 里累计已推荐 mealId，重排时过滤。

**Q28：项目里有哪些你觉得可以改进的地方？**
- 修复 `DietExceptionHandler` 包名错误（`com.diet.newdiet` → `com.diet`）；
- 明文密钥迁环境变量/配置中心；
- 反馈表关联 traceId（当前按 session 近似归属）；
- Trace 同步写库改异步（MQ）；
- 单机锁/LRU 缓存迁 Redis；
- /chat 改流式（SSE）。
- （这类问题答“项目里的真实不足 + 改进方案”最有说服力。）

## 7. 开放性 / 深挖类

**Q29：如果让你加一个新的 Agent，你会怎么加？**
- 回答框架：定义职责 → 定义结构化输入输出 → 建 Builder（模型+prompt）→ 在 Service 层封装调用+兜底 → 在 Orchestrator 加路由/事件 → 加 Trace 埋点 → 在评估里加对应指标。
- 举例：加“营养分析 Agent”：输入餐食+槽位，输出营养标签 JSON；失败走规则模板。

**Q30：如果用户量变大，哪些环节会先撑不住？怎么优化？**
- 数据库：JSON_OVERLAPS 全表扫描 → 生成列索引 / 标签表 / 向量检索；
- Trace 写入：同步写库拖慢请求 → 异步 MQ + 独立存储；
- Agent 实例：单机 LRU → 无状态化（每请求新建或 Redis 会话化）；
- LLM 成本/延迟：模型分级（已有）、流式输出、结果缓存（相同槽位复用）；
- 会话锁：单机 synchronized → 分布式锁或“按 session 路由到固定实例”。

**Q31：你怎么验证“这个推荐系统真的变好了”？**
- 三层证据：离线指标（评估报告趋势）、在线行为（反馈点赞率、换一批比例）、Bad-case 人工抽检。
- 强调闭环：每次改 prompt/规则 → 跑评估 → 对比指标 → 人工看样本。

**Q32：如果让你从零设计一个类似的 Agent 系统，你会复用哪些经验？**
- 结构化输出 + 代码校验；
- 编排层收口状态；
- 每个 LLM 调用都有降级；
- 埋点从第一天就做；
- 评估指标和业务目标对齐（准确率、成本、延迟、满意度）。

## 8. 一句话答题金句（背下来）

- “Agent 工程 = 后端工程 + 对 LLM 不确定性的治理。”
- “LLM 只负责理解和表达，决策和校验交给规则。”
- “prompt 是软约束，代码校验是硬约束。”
- “让 LLM 选菜它会幻觉，让规则选菜、LLM 解释，才是可控的。”
- “Trace 让 LLM 黑盒可回放，评估让每次迭代可量化。”
- “每一个 LLM 调用，都应该有一个不依赖 LLM 的兜底。”
- “先让链路跑通，再谈架构；先让问题暴露，再对症设计。”
